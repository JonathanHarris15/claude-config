# Triage (JIRA)

Move JIRA issues through a small state machine of triage roles. This governs the same tracker that `to-issues` and `create-epic` write into.

Every comment or description this skill posts during triage **must** begin with:

```
> *This was generated by AI during triage.*
```

## Role → JIRA mapping

Two **category** roles and five **state** roles. JIRA rarely has native statuses named `ready-for-agent` etc., so the portable representation is **labels layered on native status** — but prefer a native status/transition whenever the project's workflow already has an equivalent.

**Category** (what kind of work) → the issue **type**:
- `bug` → issue type **Bug**. Bugs are **reactive** work: file them **standalone — no parent epic, no objective due date** — and handle them as they arise. A Bug is never part of a dated epic objective. If a bug needs breaking down, add **Tasks** (sub-task level) under it.
- `enhancement` → issue type **Feature** (level 0, under the relevant epic). Planned/objective work belongs to an epic and flows through `create-epic`/`to-issues`; `triage` mainly governs incoming bugs and loose requests. If an enhancement is really a new deliverable, hand it to `to-issues` under the right epic rather than creating a loose Feature.

Hierarchy reminder: **Epic → Feature → Task** for planned work; **Bug → Task** (standalone) for reactive work. "Task" is JIRA's sub-task level.

**State** (where it is in triage) → **label** by default, native **status transition** when one matches:
- `needs-triage` — a maintainer must evaluate it
- `needs-info` — waiting on the reporter
- `ready-for-agent` — fully specified, an AFK agent can take it
- `ready-for-human` — needs a person (judgment, external access, manual testing)
- `wontfix` — will not be actioned → transition to the project's Done/Closed status with a "Won't Do"-style resolution

Every triaged issue carries exactly one category and one state. If states conflict, flag it and ask the maintainer before doing anything. These canonical names may map to different label strings per project — confirm the strings with the maintainer on first use and keep them consistent with what `to-issues`/`create-epic` apply.

## Invocation

The maintainer invokes `/triage` with natural language. Interpret and act:
- "Show me anything that needs my attention"
- "Let's look at PROJ-42"
- "Move PROJ-42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query with JQL (see `<jira-mechanics>`) and present three buckets, oldest first:
1. **Untriaged** — no state label and not yet in a triaged status.
2. **`needs-triage`** — evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation.

Show counts and a one-line summary per issue. Let the maintainer pick.

## Triage a specific issue

1. **Gather context.** Read the full issue with `getJiraIssue` (include `comment` in fields): description, comments, labels, type, reporter, dates, status. Parse prior triage notes so you don't re-ask resolved questions. Explore the codebase using `CONTEXT.md` vocabulary, respecting ADRs in the area. Read `.out-of-scope/*.md` and surface any prior rejection resembling this issue.

2. **Recommend.** Tell the maintainer your category + state recommendation with reasoning, plus a brief codebase summary relevant to the issue. Wait for direction.

3. **Reproduce (bugs only).** Before grilling, attempt reproduction — read the steps, trace the code, run tests/commands. For a disciplined loop, use `diagnose`. Report the outcome: successful repro with the code path, failed repro, or insufficient detail (a strong `needs-info` signal). A confirmed repro makes a much stronger agent brief.

4. **Grill (if needed).** If the issue needs fleshing out, run a `grill-with-docs` session.

5. **Apply the outcome:**
   - `ready-for-agent` — post an **agent brief** comment (below), then apply the state.
   - `ready-for-human` — same brief structure, but note why it can't be delegated.
   - `needs-info` — post triage notes (below), apply the state.
   - `wontfix` (bug) — polite explanation comment, then transition to Done/Closed with a "Won't Do" resolution.
   - `wontfix` (enhancement) — write the rejection to `.out-of-scope/`, comment linking the reasoning, then close.
   - `needs-triage` — apply the state; optional comment if there's partial progress.

## Quick state override

If the maintainer says "move PROJ-42 to ready-for-agent", trust them. Confirm what you're about to do (label/status changes, comment, transition), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief written first.

## Agent brief comment

A durable brief so an AFK agent (or human) can act without this conversation:

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Goal:** what "done" looks like, in one or two sentences.
**Context:** the relevant modules (CONTEXT.md vocabulary), how they fit, any ADRs that constrain the work.
**Repro / evidence:** confirmed reproduction steps and the code path (for bugs), or the user stories driving it (for enhancements).
**Approach:** the vertical slice(s) to build; acceptance criteria as a checklist.
**Out of scope:** what NOT to touch.
```

For `ready-for-human`, add a **Why a human:** line (judgment call, external access, design decision, manual testing).

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**
- point 1
- point 2

**What we still need from you (@reporter):**
- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable.

## Resuming a previous session

If prior triage notes exist on the issue, read them, check whether the reporter has answered outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

<jira-mechanics>

Load the Atlassian tools first (deferred) in one call:

```
ToolSearch → jira search issues
```

The Atlassian connector's server prefix differs per install (and changes if it's reinstalled), so never hardcode it — read the prefix off what that call returns, then load the whole set in one further `ToolSearch → select:…` using that prefix with: `getAccessibleAtlassianResources`, `searchJiraIssuesUsingJql`, `getJiraIssue`, `editJiraIssue`, `addCommentToJiraIssue`, `getTransitionsForJiraIssue`, `transitionJiraIssue`.

**Discovery.** `getAccessibleAtlassianResources` → `cloudId`. Confirm the target project key with the maintainer.

**Finding work** with `searchJiraIssuesUsingJql` (include `comment` in `fields` when you need history):
- Untriaged: `project = PROJ AND labels is EMPTY AND statusCategory != Done ORDER BY created ASC` (adapt to the project's untriaged convention).
- In triage: `project = PROJ AND labels = "needs-triage" ORDER BY created ASC`.
- Needs re-eval: `project = PROJ AND labels = "needs-info" AND updated > "-14d" ORDER BY updated ASC`, then check whether the latest comment is from the reporter.
- Ready queue: `project = PROJ AND labels = "ready-for-agent" ORDER BY created ASC`.

**Applying a state.**
- Label-based (default): read current labels with `getJiraIssue`, then `editJiraIssue` with `fields: {"labels": [...]}` — remove any old state label and add the new one in the same call (JIRA replaces the whole array). Keep exactly one state label.
- Status-based (preferred when the workflow has a matching status): `getTransitionsForJiraIssue` to find the transition id, then `transitionJiraIssue`. For `wontfix`, transition to Done/Closed and set the resolution in the transition `fields` (e.g. `{"resolution": {"name": "Won't Do"}}`). If a reopened issue is stuck, clear the resolution via `editJiraIssue` with `{"resolution": null}` first.

**Category.** Set/confirm the issue type when creating; to reclassify an existing issue, change its type via `editJiraIssue` (`fields: {"issuetype": {"name": "Bug"}}`) where the project allows it, else use a `bug`/`enhancement` label.

**Comments.** `addCommentToJiraIssue` with `contentFormat: "markdown"`. Every comment starts with the AI disclaimer line.

**Creating an issue** (when the maintainer wants one): `createJiraIssue` with the right type; apply `needs-triage` (or, if fully specified, `ready-for-agent` with an agent brief comment). Load `createJiraIssue` via ToolSearch if not already loaded.
- **Bug** — create it **standalone: do not set `parent`**, and do not set an objective `duedate`. Bugs live outside the epic tree. Break down via **Tasks** (sub-task level, `parent` = the Bug's key) only if needed.
- **Enhancement** that's really a new deliverable — prefer routing to `to-issues` to create it as a **Feature** under the right epic, rather than a loose issue.

</jira-mechanics>
